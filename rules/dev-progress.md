- 같은 이미지도 매 250ms 캡처에서 중복 비교 전에 `readImage()`·`toDataURL()`로 읽고 PNG 인코딩하는 경로를 확인했다.

- `npm run typecheck`, `npm test`(50개), `npm run build`, `npm run dist` 통과. 표준 경로 `release/copy-manager Setup 0.3.0.exe` 생성. 기존 설치본 교체는 하지 않았다. 수정 전 설치본 5초 유휴 샘플은 본체 CPU 시간 0.062초(코어 1개 기준 약 1.24%). 수정 후 실제 설치본 CPU·GUI 전후 비교는 미검증이며 95%는 호출 수 감소치다.
- 이후 사용자 요청으로 `C:/Users/user/AppData/Local/Programs/copy-manager/`에 무인 교체(설치 종료 코드 0)·재실행했다. 설치 중 `clip-history.json`, `settings.json` SHA-256이 보존됐고 패키지/설치본 app.asar SHA-256 `D262B09DD59DC2477EF618B1F5EB6BCBFC65637DECF182AD2076DE6A47C08F4F`가 일치한다. 본체 1개·감시 1개, READY 로그와 앱 응답 확인.

## 2026-10-16 저장 대기열 메모리 수정

- 사용자 증상: 프로세스가 종료되어 Ctrl+Alt+V가 반응하지 않음. 설치본 재실행 후 사용자가 창 열림을 확인했다. 이전 종료의 충돌 로그는 확보하지 못해 종료 원인은 확정하지 않았다.
- 약 250MB 히스토리에서 저장 대기 요청마다 전체 JSON·암호문을 미리 만드는 경로를 확인했다. `ClipboardStore.save()`는 이제 호출 당시 항목 상태만 복사하고 content 문자열은 공유하며, JSON 변환·암호화는 이전 저장이 끝난 뒤 수행한다. 저장 순서·핀·사용 시각·임시 파일 교체를 보존한다.
- 회귀 테스트: 첫 디스크 저장을 막은 상태에서 10회 요청해 암호화가 1회만 실행됨을 확인했다(수정 전 10회로 실패). 호출 당시 상태 보존과 암호화 실패 후 저장 복구를 포함해 3개 추가했다.
- 검증: `npm run typecheck`, `npm test` 46개, `npm run dist`, `git diff --check` 통과. 기존 Windows 감시 테스트 1회 실패 뒤 단독 재실행 및 전체 재실행에서 통과했다.
- 원본 작업공간의 `release/copy-manager Setup 0.3.0.exe`로 설치본 교체(종료 코드 0). 설치 중 히스토리 SHA-256 동일, 패키지·설치본 app.asar SHA-256 `8389465079D6F0F157D1BAB56F378792E11FBA0210B0546FFF44F8EB57947432` 일치. 설치 경로에서 재실행 후 감시 시작 로그와 프로세스 응답을 확인했다.
- 한계: 전체 히스토리 로드·렌더링의 기본 메모리 사용량은 남는다. 교체 후 단축키의 실제 UI 확인과 장기 사용 중 종료 재발 여부는 미확인이다.
